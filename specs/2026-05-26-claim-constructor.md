# ТЗ: AI-конструктор претензий

**Дата:** 2026-05-26
**Статус:** vision-уровень, без жёстких сроков
**Текущее состояние:** работающий MVP-прототип в [claim-constructor/index.html](../claim-constructor/index.html)

---

## 1. Резюме

Веб-конструктор, который помогает обычному человеку без юридических знаний составить грамотную претензию по возврату товара за 5–10 минут — без страха «белого листа» и без оплаты юриста.

Сейчас существует MVP-прототип на чистом HTML/CSS/JS с 5-экранным wizard'ом, 3 шаблонами претензий, mock-справочником ИНН и выгрузкой в `.txt`. ТЗ описывает путь от прототипа к коммерческому продукту.

---

## 2. Проблема и зачем сейчас

### Боль пользователя
Главная боль — **«не знаю, как составить документ»**:
- пугает белый лист и юридический язык
- неясно, на какие статьи ссылаться
- неясно, какие данные нужны в шапке
- неясно, что делать с готовым текстом дальше

Вторичные боли (можно адресовать позже):
- «не знаю, какие у меня права»
- «юрист слишком дорогой за типовой документ»
- «не знаю, что делать после отправки»

### Контекст рынка (по итогам исследования)
- В РФ есть готовые конкуренты: Гарант-конструктор, freshdoc.ru, sprutlex, Финграмота.рф — преимущественно шаблоны без AI
- Роспотребнадзор раздаёт образцы бесплатно
- По данным Роспотребнадзора, **60% споров решаются досудебно**, если претензия составлена грамотно — сильное обещание ценности
- Свободная ниша: продукт, который сочетает «умную» персонализацию под обстоятельства и качество шаблона, проверенного юристом

## 3. Метрики успеха

Для vision-уровня — направляющие метрики, не KPI:

- **Conversion**: % пользователей, дошедших с лендинга до скачивания/оплаты документа
- **Completion time**: медиана времени от старта до получения документа (целевой бенчмарк — ≤7 минут, как обещано на лендинге)
- **Satisfaction**: NPS / опрос «помогло ли решить ситуацию»
- **Resolution rate** (метрика второго порядка, через follow-up): % пользователей, чьи претензии были удовлетворены — единственный способ доказать ценность по сравнению с бесплатными образцами

---

## 4. Целевой пользователь

**Основной:** обычный потребитель 25–55 лет, купил товар, столкнулся с проблемой возврата. Не юрист. Возможно, никогда не писал претензий.

**Уровень технической подготовки:** низкий-средний. Пользуется маркетплейсами, госуслугами, банковскими приложениями. Не любит регистрации, не любит длинные формы.

**Эмоциональное состояние:** уже раздражён ситуацией с товаром. Любое трение — риск отвалиться.

**Сегменты вне фокуса v1**: юристы (другой продукт), малый бизнес (другая юр.специфика).

---

## 5. Пользовательский путь (core experience)

```
Лендинг → выбор ситуации → данные о товаре → реквизиты продавца
       → описание + данные пользователя → готовый документ → действия
```

Core action (одно действие, ради которого продукт существует):
**получить готовый текст претензии, который не стыдно отнести в магазин.**

Всё остальное (PDF, оплата, аккаунты, трекинг) — обвязка вокруг этого действия.

## 7. Открытые архитектурные вопросы и трейд-офы

Эти решения принимаются на этапе детального планирования v1.0. ТЗ фиксирует варианты с последствиями.

### 7.1. AI: какой подход

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Гибрид (рекомендуется)** | LLM классифицирует ситуацию из описания и выбирает блоки + статьи; финальный текст склеивается из проверенных юристом фрагментов | Минимум галлюцинаций; честно отражает «AI» в названии; контролируемое качество | Сложнее разработка; нужна работа юриста над библиотекой блоков |
| **Чистый LLM** | LLM пишет весь текст с нуля под обстоятельства | Максимальная персонализация; меньше работы юриста | Риск «уверенного бреда» (выдуманные статьи, искажённые формулировки); ПДн пользователя уходят в API |
| **Шаблоны без AI** | Текущий подход MVP, расширенный набором вопросов | Дешёво, предсказуемо, конфиденциально | Слово «AI» придётся убрать с лендинга; продукт не отличается от существующих конструкторов |

**Рекомендация:** гибрид. Чистый LLM — слишком высокий юр.риск для продукта, претендующего на доверие.

### 7.2. Бизнес-модель

| Вариант | Когда подходит |
|---|---|
| **Pay-per-PDF (199–499₽)** | Если основная аудитория — разовые пользователи. Низкий порог, высокая конверсия. Уже обещано на лендинге («оплата за PDF») |
| **Подписка** | Если делаем личный кабинет + историю + трекинг сроков + новые сценарии. Требует retention-механики |
| **Freemium + допуслуги** | Базовый PDF бесплатно, платное: проверка юристом (1500–3000₽), отправка письма за пользователя (500₽), составление иска |

**Рекомендация:** стартовать с pay-per-PDF (минимум сложности, соответствует обещанию лендинга), эволюционировать в freemium по мере появления допуслуг.

### 7.3. Аккаунты и хранение ПДн

Зависит друг от друга:

**Сценарий А: без аккаунтов, без хранения ПДн на сервере**
- Все данные только в браузере (как сейчас)
- Сервер видит данные только в момент генерации PDF и оплаты, не хранит
- НЕ нужна регистрация оператора ПДн в РКН (или нужна минимальная)
- Не нужны соглашения и UX вокруг согласий
- Минус: нет повторных визитов, нет трекинга сроков, нет истории

**Сценарий Б: опциональные аккаунты, хранение ПДн в РФ**
- Регистрация оператора ПДн в РКН (152-ФЗ)
- Хостинг строго в РФ (Selectel, Yandex Cloud, VK Cloud)
- Шифрование ПДн в БД
- Согласие на обработку ПДн на каждой форме
- Право на удаление / выгрузку данных
- Плюс: retention, трекинг 10-дневного срока, личный кабинет

**Рекомендация:** v1.0 — сценарий А. Сценарий Б — отдельный проект, когда продукт докажет product-market fit.

### 7.4. Технический стек

Действующее ограничение CLAUDE.md («один HTML, без библиотек») имело смысл для учебного MVP. Для коммерческой версии нужно решить:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Остаться на vanilla** + лёгкий бэкенд | Преемственность, контроль, нулевой бандл | Растущая сложность UI станет тяжёлой; найм разработчиков сложнее |
| **Переход на React/Vue + бэк** | Стандартный стек, легче нанимать, есть готовые компоненты для форм/PDF | Перепись фронта, бандл, потеря «прозрачности» прототипа |
| **Гибрид: фронт vanilla, бэкенд на Python/Node** | Минимум переписи, бэкенд решает задачи, для которых vanilla не подходит | Двойная компетенция в команде |

**Рекомендация для решения позже:** проверить, насколько фронт «треснет» при добавлении P1-фич (фото, личный кабинет — если идём по сценарию Б). Если выдержит — vanilla. Если нет — React.

### 7.5. Каналы привлечения

Ранний выбор каналов влияет на продукт (SEO требует контентных страниц, контекст — лендингов под запросы):

- **SEO/Google/Yandex**: «как вернуть товар», «образец претензии» — высокий intent, но дорогая выдача
- **Контекстная реклама**: Yandex Direct по «горячим» запросам — быстрая проверка спроса, дорого
- **Контент в VK/Telegram**: кейсы «как я вернул деньги» — медленный, но дешёвый канал

**Заложить в задел:** структура URL под SEO (отдельные посадочные страницы по типам ситуаций), микроразметка `HowTo`, открытый граф для соцсетей.

## 8. Нефункциональные требования

- **Производительность**: загрузка лендинга < 1.5с на 4G; генерация PDF < 5с
- **Адаптив**: mobile-first, проверено на iOS Safari и Android Chrome
- **Доступность**: контрастность WCAG AA, tab-навигация, минимальные touch-цели 44×44
- **Конфиденциальность**: HTTPS обязателен; для сценария Б — 152-ФЗ compliance
- **Уровень риска юр.ошибки**: шаблоны проходят ревью юриста по ЗПП перед каждым релизом

## 9. Юридические и продуктовые риски

| Риск | Митигация |
|---|---|
| Шаблон оказался юридически некорректным | Ревью юристом перед релизом; пометки «это не консультация»; версионирование шаблонов |
| LLM сгенерировал ссылку на несуществующую статью | Гибридный подход (LLM не пишет статьи, только выбирает блоки); ручная проверка золотого набора кейсов |
| Утечка ПДн пользователя | Сценарий А (не хранить); для сценария Б — шифрование, аудит, ограниченные роли |
| Mismatch ожиданий: «AI» в названии vs шаблонная логика | Либо гибридная AI, либо честный ребрендинг в «конструктор» |
| Пользователь применил документ и проиграл — обвиняет сервис | Дисклеймеры (уже есть в MVP); видимый CTA на платную проверку юристом для сложных случаев |
| Конкурент с большим маркетинговым бюджетом | Дифференциация через UX (7 минут vs «заполни 20 полей») и пост-документную инструкцию |
